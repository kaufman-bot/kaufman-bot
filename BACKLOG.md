# Backlog

Осознанно отложенный технический долг. Пункты не блокируют текущую функциональность; для пунктов 1–2 условие исполнения — внедрение Redis; пункты 3–10 независимы от него.

## 1. Sweep плагинов: in-process флаг → Redlock

- **Где:** `backend/src/plugins/bot-plugins.service.ts`, поле `sweeping`
- **Сейчас:** `boolean`-флаг запрещает параллельные sweep'ы только внутри одного процесса. В prod cluster (`ecosystem-prod.config.cjs`, `exec_mode: 'cluster'`) каждый воркер запускает свой sweep — фоновая работа дублируется по числу воркеров. Корректность при этом не страдает: задачи захватываются атомарно условным `updateMany` (PENDING→PROCESSING), повторной обработки нет.
- **Что сделать:** после внедрения Redis заменить флаг на распределённую блокировку (Redlock) — один sweep на все инстансы, чтобы можно было горизонтально масштабировать сервис без дублирования фоновой работы.

## 2. Шина событий чата: RxJS Subject → event bus / очередь

- **Где:** `backend/src/services/chat-events.service.ts`, `subject = new Subject<ChatEvent>()`
- **Сейчас:** события живут в памяти процесса: не доставляются другим инстансам в cluster-режиме (подписчики каждого воркера видят только события своего процесса) и теряются при рестарте сервера. Пропуск компенсируется на клиенте повторной загрузкой истории при переподключении SSE.
- **Что сделать:** после внедрения Redis (или другого брокера) перевести доставку `ChatEvent` на event bus / очередь (Redis pub/sub или Streams, BullMQ, NATS — выбрать при реализации): события переживают рестарт и доставляются подписчикам всех инстансов; после этого компенсирующий refetch истории на фронте можно будет убрать.

## 3. Регистрация плагинов: явный список в AppModule → автоподключение

- **Где:** `backend/src/app.module.ts`, провайдер `BOT_PLUGINS` (`useFactory` + `inject`)
- **Сейчас:** подключение нового плагина требует правки AppModule: добавить провайдер класса и запись в `inject` фабрики `BOT_PLUGINS` (порядок = приоритет). Ядро знает все плагины явно: с ростом их числа растут правки общего файла, риск забыть регистрацию (tsc и сборка при этом проходят без ошибок) и конфликты правок.
- **Что сделать:** декларативное самоподключение — плагин помечается декоратором `@BotPlugin()`, а массив `BOT_PLUGINS` собирается автоматически: сканированием контейнера (DiscoveryModule из `@nestjs/core`) в `OnModuleInit`/`OnApplicationBootstrap` либо через общий динамический `PluginsModule`, в который плагины вносят себя. Подключение плагина = создать класс (и/или импортировать его модуль) — без правок AppModule и без фабрики; приоритет диспетчеризации при этом переносится в поле декоратора (например `order`).
- **Условие:** Redis не требуется; пункт независим от 1 и 2.

## 4. Модули NestJS: PrismaModule и SeedModule → плоский AppModule

- **Где:** `backend/src/prisma/prisma.module.ts`, `backend/src/seed/seed.module.ts` (+ реэкспорт в `prisma/index.ts`)
- **Сейчас:** два инфраструктурных сервиса обёрнуты в собственные модули: PrismaModule экспортирует PrismaService, SeedModule импортирует его ради SeedService; AppModule подключает оба. Лишний слой косвенности: путь зависимости PrismaService проходит через два файла, при этом остальные ~десяток сервисов и все контроллеры уже перечислены напрямую в AppModule.
- **Что сделать:** убрать PrismaModule и SeedModule; PrismaService и SeedService зарегистрировать обычными провайдерами AppModule (DI по токену класса внутри одного модуля работает без `exports`). Целевое состояние — ровно один собственный модуль NestJS (AppModule); сторонние модули (ObserveModule.forRoot, ServeStaticModule) остаются в imports.
- **Условие:** Redis не требуется; не конфликтует с пунктом 3 (decorator + discovery работает и в одном модуле). Обратный ход — возврат фиче-модулей — станет актуальным при росте фиче-границ.

## 5. Локализация ответов бота: таблица текстов в плагине → общий i18n

- **Где:** `backend/src/plugins/settings.plugin.ts` (`TEXTS`/`LANGUAGE_TITLES`), `backend/src/plugins/ping-pong.plugin.ts`, `backend/src/plugins/time.plugin.ts`
- **Сейчас:** активный язык пользователя хранится в `User.language` и применяется только в `SettingsPlugin` — его экран и подтверждение смены языка. Остальные реплики бота языком не управляются: `pong` и строка времени (`2026-11-01 12:34:56 (Europe/Moscow)`) всегда английские, как и тексты ошибок валидации. Перевод живёт отдельной таблицей `{ en, ru }` внутри плагина; каждая новая локализуемая строка требует своей таблицы, а контракт плагина (`BotPluginReply`) не передаёт язык.
- **Что сделать:** общий i18n-слой бэкенда — словари по кодам языка (`en`, `ru`), резолв активного языка из контекста запроса и хелпер типа `t(user, key)`. Плагины получают уже локализованные строки, собственные таблицы текстов исчезают; при необходимости локализация описаний ошибок (`BadRequestException`) и, отдельным шагом, ответа `Language` в REST-контракте.
- **Условие:** Redis не требуется; пункт независим от 1–4. Точка расширения обозрима: активный язык уже лежит в `User.language` и попадает в `BotPluginContext` вместе с `user`, поэтому общий i18n не требует ни миграции схемы, ни смены контракта диспатча.

## 6. Telegram Bridge: polling-фолбэк

- **Где:** `backend/src/services/telegram-bridge.service.ts`, `backend/src/services/telegram-webhook.service.ts`
- **Сейчас:** доставка входящих обновлений работает исключительно через вебхук: Telegram ходит на `POST /api/telegram/webhook/:botId`. При недоступном публичном HTTPS (dev без ngrok, временный сетевой сбой) бот не получает сообщения.
- **Что сделать (do):** long-polling `getUpdates` как фолбэк: при недоступности вебхука (или когда `TELEGRAM_WEBHOOK_BASE_URL` пуст) — стартовать поллинг для активных ботов с корректным `offset` и graceful stop при появлении вебхук-URL.
- **Условие:** Redis не требуется; для cluster — только после Redis-дедуп (#7), чтобы два воркера не поллили один бот.

## 7. Telegram Bridge: Redis-дедуп исходящей доставки в cluster

- **Где:** `backend/src/services/telegram-bridge.service.ts`, `ecosystem-prod.config.cjs` (`instances: 1`)
- **Сейчас:** `ChatEventsService` — in-memory `Subject`; при `instances > 1` каждый воркер подписан на свои события и форвардит BOT-ответ в Telegram, порождая дубль. Единственная защита — `instances: 1`.
- **Что сделать (when):** после внедрения Redis (#1/#2) — идемпотентная отправка по `messageId` (SETNX `tg-sent:{messageId}` TTL 24h или stream consumer group): один ответ → один Telegram-send вне зависимости от числа воркеров. После проверки — поднять `instances` в `ecosystem-prod.config.cjs`.
- **Условие:** требует Redis (#1/#2).

## 8. Telegram Bridge: медиа и кэпшены

- **Где:** `backend/src/services/telegram-bridge.service.ts`
- **Сейчас:** мост пересылает только текстовые сообщения и inline-кнопки. Изображения, документы, голосовые, видео и фотокэпшены из Telegram не обрабатываются; исходящие медиа тоже не отправляются (у модели `Message` нет полей `mediaType`/`mediaUrl`).
- **Что сделать (when):** расширить `Message` полем `media` (или `attachments: Json?`), реализовать `sendPhoto`/`sendDocument`/… в `TelegramSender`, входящие `photo`/`document` → скачивание file_id → сохранение (MinIO/диск) → запись в БД.
- **Условие:** независим от Redis; объёмная задача, требует продуктовых решений (хранилище, лимиты).

## 9. Унификация лимита `callback_data` (Telegram 64 vs проект 256)

- **Где:** `backend/src/utils/keyboard-buttons.ts` (`MAX_CALLBACK_LENGTH = 256`), `backend/src/services/telegram-bridge.service.ts` (`TG_CALLBACK_DATA_MAX_BYTES = 64`)
- **Сейчас:** внутренний лимит `callbackData` — 256 символов (веб-чат, моки, пресеты). Telegram принимает максимум 64 **байта** UTF-8. Мост молча отбраковывает кнопки, не помещающиеся в 64 байта, и отправляет сообщение текстом без клавиатуры. Оператор, создавший кнопку с `callbackData` 65–256 символов, видит её в веб-чате, но в Telegram она не появится.
- **Что сделать (do):** унифицировать: либо снизить проектный `MAX_CALLBACK_LENGTH` до 64 (ломает существующие пресеты/сообщения — миграция), либо добавить валидацию на уровне Telegram-отправки с явным предупреждением оператору, либо реализовать inline-кнопки через `web_app` / `copy_text` (для длинных payload). Решение принимается с учётом обратной совместимости.
- **Условие:** Redis не требуется.

## 10. Ошибки фронтенда: недоступный бэкенд ≠ «Неверный API-ключ»

- **Где:** `frontend/src/app/session.service.ts` (`login`, `restore` /
  `restoreStoredKey`), `frontend/src/app/login/login.component.ts`, `frontend/src/app/chat.service.ts`, `frontend/src/app/mock-bot.service.ts`, `frontend/src/app/telegram-bots-admin.service.ts`
- **Сейчас:** все HTTP-сбои схлопнуты в маркер «пусто», поэтому UI физически не может различить причины. `login()` в `catchError` вызывает `logout()` и отдаёт `of(null)`, а `LoginComponent` на любой `null` печатает «Неверный API-ключ»: при незапущенном бэкенде (`status: 0`, 502/504 от dev-прокси, 500) пользователя обвиняют в его ключе и он идёт перепроверять ключ вместо того чтобы поднять сервер. Второй симптом (устранён, см. пункт 3 ниже): `validateStoredKey()` при любой ошибке молча стирал ключ из `localStorage`, а сама проверка не отправлялась вовсе из-за DI-цикла «конструктор сервиса → интерцептор → этот же сервис», поэтому F5 каждый раз возвращал на страницу входа. В остальных сервисах тот же паттерн (`catchError(() => of([]))` / `of(null)`): пустой список диалогов, неотправленное сообщение и «клик не сработал» неотличимы от 401/403/404/500.
- **Что сделать (do):**
  1. ~~Общий маппинг `HttpErrorResponse → сообщение`~~ — **частично сделано:** `frontend/src/app/utils/api-error.ts` (`describeApiError`) уже существует и подключён в `TelegramBotsAdminService.setTarget` (пункт #11, выполнен); остаётся применить его остальным точкам и при необходимости дополнить тело `ApiErrorDto`.
  2. `SessionService.login()` — не проглатывать ошибку, а отдавать различимый результат (`{ ok: false, reason }` либо проброс `ApiError` в `error`), `LoginComponent` выводит разные тексты для «ключ отклонён» и «сервер недоступен».
  3. ~~`validateStoredKey()` — стирать сохранённый ключ только при 401/403~~ —
     **сделано:** проверка при загрузке страницы вынесена из конструктора в
     идемпотентный `SessionService.restore()` (ключ подставляется в запросы до
     ответа сервера, guards ждут `whenReady()`), ключ стирается только при
     `401`/`403`, при `status 0`/`50x`/timeout остаётся; форма входа
     подставляет сохранённый ключ с подсказкой. Баннер «нет связи с сервером»
     (вместо страницы входа) и ретрай после восстановления SSE — **не**
     сделано: при недоступном бэкенде пользователь по-прежнему видит `/login`,
     но с уже заполненным полем. Подробности DI-цикла —
     [docs/pitfalls.md](docs/pitfalls.md#http-in-constructor-interceptor-cycle).
  4. Сервисы чата/консоли/админки — вместо `of([])`/`of(null)` сохранять ошибку в сигнал, чтобы компоненты рисовали «не удалось загрузить: <причина>» и «сообщение не отправлено» вместо пустого экрана.
- **Условие:** Redis не требуется; независимо от остальных пунктов. Тексты сообщений локализуются через будущий i18n (#5), до него — как в существующих компонентах.
