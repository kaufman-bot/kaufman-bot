# Git Onboarding Commits — Perесборка изменений в обучающую серию коммитов

## Назначение

Превратить набор изменений (рабочие файлы, WIP-коммиты, фича-ветку) в последовательность коммитов, читая которые по порядку, ревьюер погружается в контекст задачи: что сделано, зачем и в каком порядке это стоит понимать. История коммитов — обучающий материал, а не хронология реальной работы.

## Когда применять

- Перед созданием PR/merge request, когда изменения накопились как WIP или один большой коммит.
- Когда нужно «причесать» историю для ревью.
- Когда фича-ветка содержит хаотичные коммиты и нужна чистая линейная история.

## Параметры

| Параметр | По умолчанию                   | Описание                                                     |
| -------- | ------------------------------ | ------------------------------------------------------------ |
| BASE     | `main`                         | Базовая ветка/коммит — точка, от которой считаются изменения |
| SOURCE   | текущая ветка (или WIP-коммит) | Ветка/коммит с итоговым состоянием кода                      |
| TARGET   | `<SOURCE>-onboarding`          | Имя новой ветки для серии                                    |

Если есть незакоммиченные изменения — сначала закоммить их во временный WIP-коммит на текущей ветке, чтобы зафиксировать SOURCE.

## Правила безопасности

- **Никогда не изменяй BASE и SOURCE** — никаких `reset`, `rebase`, `amend`, `push` на них.
- **Не делай `push` и `force`-операций** вообще. Вся работа — только в ветке TARGET.
- **Не используй интерактивные команды** (`git add -p`, `git rebase -i`, редакторы).
- Если TARGET уже существует — остановись и спроси пользователя.
- Если что-то пошло не так — не чини историю SOURCE; удали TARGET и начни заново.

## Шаг 1. Анализ и план

1. Изучи `git diff BASE...SOURCE --stat` и полный diff. Пойми суть изменений целиком.
2. Составь план серии и покажи его таблицей:

| №   | Заголовок коммита     | Файлы/части | Почему этот шаг здесь               |
| --- | --------------------- | ----------- | ----------------------------------- |
| 0   | cover letter (пустой) | —           | Обзор серии, карта, с чего начинать |
| 1   | ...                   | ...         | ...                                 |
| N   | ...                   | ...         | ...                                 |

3. Принципы плана:
   - **Порядок от фундамента к деталям:** типы/контракты/схема → доменная логика → интеграция (API, UI, конфиги) → тесты → документация. Если для понимания лучше сначала показать каркас и интерфейсы, а потом наполнение — делай так.
   - **Один коммит = одна мысль**, объяснимая в 2–5 предложений. Ориентир: 3–12 коммитов, без коммитов-«свалок».
   - **Никакого мёртвого кода:** нельзя добавлять то, что будет существенно переписано или удалено в следующих коммитах серии.
   - **Каждый коммит по возможности собирается** и проходит линтер.
   - **Механические изменения** (форматирование, переименования, перемещения) выноси в отдельные коммиты.

4. **Дождись подтверждения плана**, прежде чем создавать коммиты.

## Шаг 2. Создание коммитов

### 2.1. Создание ветки

```bash
git switch -c TARGET BASE
```

### 2.2. Cover letter (коммит 0)

Пустой обзорный коммит — общая цель изменений, карта серии, ключевые понятия, с чего начинать чтение.

```bash
git commit --allow-empty -m "<заголовок>"
```

### 2.3. Для каждого шага плана

**Файл целиком в итоговом виде:**

```bash
git checkout SOURCE -- <path>
```

**Удалённый файл:**

```bash
git rm <path>
```

**Файл, который появляется по частям:** запиши промежуточную версию вручную; итоговую версию всегда бери через `git checkout SOURCE -- <path>`.

**Проверка staging:**

```bash
git diff --cached   # в коммит входит только то, что заявлено в плане
```

**Сообщение коммита** — формат:

```
<тип>(<область>): <короткий заголовок до 72 символов>

Что: что именно добавляет этот шаг.
Зачем: какую проблему решает и почему этот шаг идёт здесь.
Как читать: с какого файла/функции начать, на что обратить внимание.
Решения: какие альтернативы рассматривались и почему отброшены (если были).
Дальше: что появится в следующем коммите (одна строка).

Step: N/TOTAL
```

## Шаг 3. Финальная проверка

### 3.1. Совпадение деревьев

```bash
git diff --exit-code SOURCE TARGET
```

Итоговое дерево TARGET **обязано** совпадать с SOURCE полностью. Если есть расхождения — найди, в каком коммите ошибка, и исправь серию (только в TARGET) до полного совпадения.

### 3.2. Лог серии

```bash
git log --oneline BASE..TARGET
```

### 3.3. Отчёт пользователю

Покажи:

- Сколько коммитов создано.
- Где промежуточные версии файлов написаны вручную (их стоит перепроверить).
- Какие коммиты не собираются по отдельности.
- Как удалить ветку, если результат не понравился:
  ```bash
  git switch <SOURCE> && git branch -D <TARGET>
  ```

## Перенос в текущую ветку (опционально)

Если пользователь хочет, чтобы коммиты были в текущей ветке (а не в TARGET):

```bash
git switch <current_branch>
git reset --hard <BASE>
git cherry-pick <first_onboarding_commit>^..<last_onboarding_commit>
# Для пустого cover letter: git commit --allow-empty --no-edit при cherry-pick
git branch -D <TARGET>
```

## Примеры типов коммитов

| Тип        | Когда использовать                             |
| ---------- | ---------------------------------------------- |
| `feat`     | Новая функциональность                         |
| `fix`      | Исправление бага                               |
| `refactor` | Переструктурирование без изменения поведения   |
| `test`     | Тестовая инфраструктура, конфигурация раннеров |
| `ci`       | CI/CD конфигурация                             |
| `chore`    | Конфигурация, зависимости, инфраструктура      |
| `docs`     | Документация                                   |
| `style`    | Форматирование, переименования (без логики)    |

## Антипаттерны

- **Коммит-«свалка»** — все изменения в одном коммите. Ревьюер не может понять порядок.
- **Мёртвый код** — добавлен в одном коммите и удалён/переписан в следующем.
- **Нарушение сборки** — коммит не компилируется и это не указано в сообщении.
- **Слишком мелкая нарезка** — коммиты по 1 строке, которые логически одно изменение.
- **Изменение BASE/SOURCE** — никогда, даже если «удобно».
