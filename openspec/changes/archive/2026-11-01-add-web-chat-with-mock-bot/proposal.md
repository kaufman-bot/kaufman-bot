# Proposal

## Why

Проект задуман как Telegram-бот, но интеграция с Telegram в этой задаче не делается. Чтобы развивать диалоговую логику бота, нужен веб-чат пользователя с ботом (фронт + бэк) и мок-сервер бота — веб-интерфейс оператора, который симулирует получение сообщений от пользователей и ответы на них. Доступ к веб-интерфейсам должен работать по уже существующей в проекте модели API-ключей, поэтому требуется и сам вход по ключу.

## What Changes

- **Вход по API-ключу (бэк + фронт)**: новый эндпоинт `POST /api/v1/auth/login`, принимающий введённый пользователем API-ключ и возвращающий профиль (`user` + `apiKey`) — тот же контракт, что у `GET /auth/me`; на фронте — страница входа, хранение ключа в браузере и автоматическая передача ключа (`x-api-key`) во всех последующих запросах к бэкенду.
- **Веб-чат пользователя с ботом**: новая страница `/chat`, диалог 1:1 пользователя с ботом: отправка сообщений (`POST /api/v1/chat/messages`), история (`GET /api/v1/chat/messages`), живое получение ответов бота через SSE (`GET /api/v1/chat/stream`).
- **Мок-сервер бота (веб-версия чата)**: новая страница `/mock-bot` — консоль оператора: список пользователей с их диалогами (заказ по последней активности, счётчик непрочитанных), переключение между пользователями, отправка ответа от имени бота (`POST /api/v1/mock-bot/conversations/{userId}/messages`), SSE-поток о новых сообщениях пользователей (`GET /api/v1/mock-bot/stream`).
- **Навигация главной страницы**: на дашборде (`/`) появляется навигация со ссылками на чат пользователя (`/chat`) и веб-интерфейс мок-сервера (`/mock-bot`).
- **Сид двух дефолтных пользователей с ролью USER**: SeedService дополнительно создаёт двух пользователей с ролью `USER` и их API-ключами из env (`USER1_*`, `USER2_*`), идемпотентно, с пропуском с предупреждением при отсутствующих переменных (по образцу существующего сида админа).
- **Схема БД**: новые модели `Conversation` (диалог 1:1 пользователя с ботом) и `Message` (сообщение с указанием отправителя `USER`/`BOT`) — только через миграцию Prisma.
- Telegram-интеграция остаётся вне рамок этой задачи (чат работает только через веб-интерфейсы).

Допущения, принятые без отдельного вопроса:

- Консоль мок-сервера требует ключ пользователя с ролью `ADMIN` (оператор входит сидовым админ-ключом); у пользователя без роли `ADMIN` — `403`. Обе веб-страницы (чат и консоль) доступны только после входа по API-ключу: без ключа фронт перенаправляет на страницу входа.
- Реалтайм-доставка новых сообщений — через SSE по образцу существующего `/time/stream` (ApiKeyGuard уже поддерживает `?apiKey=` для EventSource); история подгружается заново при переподключении.

## Capabilities

### New Capabilities

- `api-key-login`: вход по API-ключу — проверка введённого ключа на бэке, страница входа на фронте, хранение ключа и передача его (`x-api-key`) во всех последующих взаимодействиях с бэкендом, выход и обработка потери валидности ключа.
- `user-chat`: веб-чат пользователя с ботом — REST API диалога (история, отправка), SSE-поток ответов бота и страница чата на фронте.
- `mock-bot-console`: консоль мок-сервера бота — список пользователей с диалогами и непрочитанными, переключение между пользователями, ответы от имени бота, SSE-поток новых сообщений, требования доступа по роли `ADMIN`.
- `default-user-seeding`: сид двух дефолтных пользователей с ролью `USER` (и их API-ключами) из env при старте приложения.

## Impact

- **Бэкенд** (`backend/`): новая миграция Prisma (модели `Conversation`, `Message`); новые контроллеры `ChatController`, `MockBotController` + DTO со Swagger-декораторами; расширение `SeedService` (сид двух USER-пользователей); новый эндпоинт в `AuthController`/`AuthService` (login); перегенерация `swagger.json` → SDK для e2e (`npm run generate`).
- **Фронтенд** (`frontend/`): маршруты `/`, `/login`, `/chat`, `/mock-bot`; HTTP-интерцептор с `x-api-key`; сервис сессии (хранение ключа, сигналы профиля); компоненты чата и консоли мок-сервера; навигация на дашборде; EventSource-подписки со `?apiKey=`.
- **Env**: новые переменные `USER1_EMAIL`, `USER1_PASSWORD`, `USER1_API_KEY`, `USER2_EMAIL`, `USER2_PASSWORD`, `USER2_API_KEY` в `backend/.env` и `backend/.env.example`.
- **Тесты**: e2e через сгенерированный OpenAPI SDK на реальном запущенном бэкенде (login, сценарий диалога пользователь↔бот, список в консоли, 403 для не-админа); юнит-тесты новых сервисов (Vitest) и компонентов фронта (Jest).
- **Безопасность**: доступ к чату — любой активный ключ; доступ к консоли мок-сервера — только ключ с ролью `ADMIN` (AdminGuard-паттерн).
