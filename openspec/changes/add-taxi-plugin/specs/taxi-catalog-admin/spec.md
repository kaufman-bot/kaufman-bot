# Spec Delta

## Purpose

Админские справочники такси: населённые пункты с километражем, доп. услуги с наценкой, время выезда, кол-во человек, водители со своими машинами. Полнота справочников определяет варианты, которые визард заказа предлагает пассажиру.

## ADDED Requirements

### Requirement: CRUD населённых пунктов

Система SHALL предоставлять эндпоинты `GET/POST/PATCH/DELETE /api/v1/taxi/cities` (доступ по API-ключу с ролью ADMIN) для управления населёнными пунктами такси. Населённый пункт SHALL содержать `name` (уникальное имя, непустое) и `distanceKm` (километраж вдоль маршрута от первого пункта, неотрицательное число), используемый матрицей цен. Список SHALL возвращаться упорядоченным по `distanceKm`.

#### Scenario: Создание населённого пункта

- **WHEN** ADMIN отправляет `POST /taxi/cities` с валидными `name` и `distanceKm`
- **THEN** ответ `201` содержит созданный пункт, и он появляется в списке

#### Scenario: Дубликат имени

- **WHEN** ADMIN создаёт пункт с именем, которое уже существует
- **THEN** ответ `409`, новый пункт не сохраняется

#### Scenario: Некорректные поля

- **WHEN** ADMIN отправляет пустое имя или отрицательный километраж
- **THEN** ответ `400` с телом ошибки, пункт не сохраняется

#### Scenario: Удаление пункта

- **WHEN** ADMIN удаляет пункт, на который не ссылается ни один заказ
- **THEN** ответ `204`, пункт и цены всех пар с его участием исчезают из матрицы

#### Scenario: Удаление пункта с заказами

- **WHEN** ADMIN удаляет пункт, на который ссылается хотя бы один подтверждённый заказ
- **THEN** ответ `400` с пояснением, пункт не удаляется

### Requirement: CRUD доп. услуг

Система SHALL предоставлять эндпоинты `GET/POST/PATCH/DELETE /api/v1/taxi/services` для управления доп. услугами такси. Услуга SHALL содержать `name` (непустое), `surcharge` (наценка к цене в рублях, неотрицательное число), `isActive` (отключённая услуга не показывается в визарде) и `isCarFeature` (признак «возможность машины»: услуга требует оснащения машины и учитывается автоподбором при оформлении заказа).

#### Scenario: Создание услуги

- **WHEN** ADMIN отправляет `POST /taxi/services` с валидными `name` и `surcharge`
- **THEN** ответ `201` содержит созданную услугу со значением `isActive: true` по умолчанию

#### Scenario: Отключение услуги

- **WHEN** ADMIN выставляет `isActive: false` у услуги, выбранной в существующем черновике визарда
- **THEN** услуга больше не предлагается в визарде; уже оформленные заказы сохраняют её снимок

#### Scenario: Пометка услуги как возможности машины

- **WHEN** ADMIN создаёт услугу «детское кресло» с `isCarFeature: true`
- **THEN** ответ `201` содержит услугу с признаком, и она доступна в списке возможностей при редактировании машин

#### Scenario: Некорректная наценка

- **WHEN** ADMIN отправляет отрицательную наценку или пустое имя
- **THEN** ответ `400`, услуга не сохраняется

### Requirement: CRUD времени выезда

Система SHALL предоставлять эндпоинты `GET/POST/PATCH/DELETE /api/v1/taxi/departure-slots` для управления временем выезда. Слот SHALL содержать `time` в формате `HH:MM` (уникальный), `isActive` и `sortOrder`. Список SHALL возвращаться упорядоченным по `sortOrder`, затем по времени.

#### Scenario: Создание слота

- **WHEN** ADMIN создаёт слот `09:30`
- **THEN** ответ `201`, слот появляется в списке и в визарде на шаге выбора времени

#### Scenario: Некорректный формат времени

- **WHEN** ADMIN создаёт слот с `time`, не соответствующим `HH:MM` (например `25:00` или `9-30`)
- **THEN** ответ `400`, слот не сохраняется

### Requirement: CRUD количества человек

Система SHALL предоставлять эндпоинты `GET/POST/PATCH/DELETE /api/v1/taxi/passenger-options` для управления допустимым количеством пассажиров. Вариант SHALL содержать `count` (положительное целое, уникальное) и `isActive`.

#### Scenario: Создание варианта

- **WHEN** ADMIN создаёт вариант с `count: 3`
- **THEN** ответ `201`, вариант появляется в визарде на шаге выбора количества человек

#### Scenario: Некорректное количество

- **WHEN** ADMIN создаёт вариант с `count` ≤ 0 или дублирующим существующее
- **THEN** ответ `400` (дубликат — `409`), вариант не сохраняется

### Requirement: CRUD водителей с машинами

Система SHALL предоставлять эндпоинты `GET/POST/PATCH/DELETE /api/v1/taxi/drivers` для управления водителями (имя, телефон, активность) с вложенным списком их машин через `GET/POST/PATCH/DELETE /api/v1/taxi/drivers/:driverId/cars`. Машина SHALL содержать непустые модель и уникальный госномер, обязательную вместимость `seats` (положительное целое, используется автоподбором) и опциональный `color`.

#### Scenario: Создание водителя с машиной

- **WHEN** ADMIN создаёт водителя, затем добавляет ему машину через `POST /taxi/drivers/:id/cars`
- **THEN** ответ `201` содержит машину, и она отображается в списке машин водителя

#### Scenario: Удаление водителя

- **WHEN** ADMIN удаляет водителя с машинами
- **THEN** ответ `204`, машины этого водителя удаляются вместе с ним

#### Scenario: Некорректная вместимость машины

- **WHEN** ADMIN добавляет машину без `seats`, с `seats` ≤ 0 или не-целым
- **THEN** ответ `400`, машина не сохраняется

#### Scenario: Дубликат госномера

- **WHEN** ADMIN добавляет машину с госномером, который уже есть у любого водителя
- **THEN** ответ `409`, машина не сохраняется

### Requirement: Оснащение машины возможностями-услугами

Машина SHALL декларировать список возможностей-услуг, которые она предоставляет, управляемый через эндпоинты машин (`POST/PATCH` принимают список идентификаторов услуг). В списке выбора возможностей машины SHALL предлагаться только услуги с `isCarFeature: true`. Оснащение машины SHALL учитываться автоподбором при оформлении заказа (см. `taxi-order-wizard`).

#### Scenario: Машина с возможностями

- **WHEN** ADMIN добавляет машине возможности «детское кресло» и «курение в салоне» (обе помечены `isCarFeature`)
- **THEN** ответ содержит машину с этими возможностями, и они видны в списке машин водителя

#### Scenario: Обычные услуги не предлагаются

- **WHEN** ADMIN редактирует оснащение машины, а услуга «вода для пассажира» не помечена `isCarFeature`
- **THEN** в вариантах возможностей этой услуги нет

### Requirement: Доступ к справочникам только для админов

Все эндпоинты справочников такси SHALL требовать API-ключ и роль ADMIN.

#### Scenario: Неавторизованный запрос

- **WHEN** запрос выполнен без API-ключа
- **THEN** ответ `401` с телом ошибки

#### Scenario: Не-админский ключ

- **WHEN** запрос выполнен с валидным ключом пользователя с ролью USER
- **THEN** ответ `403` с телом ошибки

### Requirement: Сид справочников по умолчанию

Система SHALL засеивать при старте дефолтные справочники такси, но только те таблицы, которые пусты. Засеянные записи SHALL оставаться редактируемыми через CRUD. Состав дефолта: маршрут Москва–Санкт-Петербург с крупными промежуточными пунктами и километражем; типовые доп. услуги; слоты времени выезда; варианты кол-ва человек.

#### Scenario: Первый запуск

- **WHEN** сервер стартует на пустой БД
- **THEN** справочники содержат города Москва (0 км), Санкт-Петербург (700 км) и промежуточные Тверь, Вышний Волочёк, Бологое, Великий Новгород, Чудово; услуги — детское кресло, перевозка животных, курение в салоне, кондиционер, музыка в салоне, тишина в салоне, помощь с багажом, вода для пассажира, зарядка для телефона; слоты 08:00, 12:00, 16:00, 20:00; варианты пассажиров 1–4

#### Scenario: Повторный запуск

- **WHEN** сервер стартует на БД, где справочники уже заполнены (в том числе частично изменены админом)
- **THEN** сид не перезаписывает и не дублирует существующие записи
