# Design

## Context

См. proposal.md (Why). Состояние, определяющее подход:

- Контракт плагина `BotPlugin` уже поддерживает multi-step-сценарии: `handlesCallbacks` (реакция на BUTTON-сообщения), `BotPluginReply` с текстом + inline-кнопками, namespace-клейм через `canHandle` — образец `SettingsPlugin`. Ошибка плагина никогда не доходит до HTTP-клиента: диспетчер глотает исключение в `Logger.error`, поэтому все отказы визарда обязаны быть **возвращёнными** репликами, а не throw.
- Сервисы разделяются на entity-CRUD и use-case (skill `service-layer-split`); контроллеры — DTO-классы со Swagger-декораторами, guard-пара `ApiKeyGuard` + `AdminGuard` как в `AdminUsersController` (`@ApiHeader x-api-key required:false`). Глобального `ValidationPipe` нет — валидация в сервисах (`BadRequestException`/`ConflictException`/`NotFoundException`).
- Схема меняется только миграциями Prisma; enum импортируются из `src/generated/prisma/enums.js` (не из `@prisma/client`). E2E идут через сгенерированный SDK на живом бэкенде; конвейер чата доставляет реплики бота в БД + SSE + Telegram-мост.
- Фронт: standalone-компоненты с inline-шаблонами, lazy `loadComponent`-роуты, guards `requireAdminGuard`, сервисы поверх SDK. Прокси `/api` → бэкенд через `proxy.conf.json`.

## Goals / Non-Goals

**Goals:**

- Полный админ-CRUD справочников такси (города, услуги, слоты, кол-во человек, водители+машины) и матрицы цен с авторасчётом.
- Визард заказа в боте как конечный автомат поверх существующего плагинного конвейера (БД-черновик, кнопки, снимок заказа).
- Автоподбор свободной машины с водителем под запрос пассажира (вместимость + возможности-услуги) при подтверждении заказа, освобождение машины при завершении/отмене.
- Витрина заказов с фильтром, назначенной машиной и сменой статуса.
- Админка как раздел `/taxi` с сайдбаром и дочерними маршрутами, пункт в navbar.
- Idempotent сид дефолтных справочников.

**Non-Goals:**

- Оплата, уведомления водителя, геолокация/карты.
- Ручное распределение и переназначение машин админом (машина подбирается автоматически; при необходимости админ отменяет заказ — машина освобождается).
- Редактирование состава оформленного заказа (только смена статуса).
- Календарные даты выезда (только ежедневные слоты `HH:MM`).
- Версионирование цен, скидки, тарифные зоны.
- Динамическая загрузка плагинов (см. BACKLOG #3).

## Decisions

### D1. Модель данных — 8 таблиц + enum статуса

Миграция `add_taxi_plugin`, все изменения аддитивные:

- `TaxiCity { id, name (unique), distanceKm Int, isActive Boolean @default(true), sortOrder Int @default(0) }` — `distanceKm` = километраж вдоль маршрута от пункта с минимальным километражем.
- `TaxiExtraService { id, name (unique), surcharge Int, isActive, isCarFeature, sortOrder }` — наценка в целых рублях; `isCarFeature` = услуга-«возможность машины», участвующая в автоподборе (детское кресло, курение в салоне и т.п.).
- `TaxiCityPrice { id, fromCityId, toCityId, price Int }` + `@@unique([fromCityId, toCityId])` — пара хранится нормализованной (D6), цена симметрична.
- `TaxiDepartureSlot { id, time String (unique, `HH:MM`), isActive, sortOrder }`.
- `TaxiPassengerOption { id, count Int (unique), isActive, sortOrder }`.
- `TaxiDriver { id, fullName, phone, isActive }`; `TaxiCar { id, driverId (FK Cascade), model, plate (unique), color?, seats Int }` — `seats` обязательная вместимость для подбора; оснащение машины — связь m-n к `TaxiExtraService` (join `TaxiCarFeature`), в ней только `isCarFeature`-услуги.
- `TaxiDriver.isActive = false` исключает его машины из автоподбора; удалить водителя/машину, занятую активным заказом, сервис отклоняет (`400`).
- `TaxiOrder { id, userId (FK Cascade), status TaxiOrderStatus, draftStep Int, fromCityId? (FK Restrict), toCityId? (FK Restrict), departureSlotId? (FK SetNull), passengerCount Int?, serviceIds Json? (черновик), carId? (FK SetNull — занятость машины при активном заказе), // снимок на момент подтверждения:
fromCityName, toCityName, departureSlotLabel, serviceSnapshot Json?, carSnapshot Json? (водитель/модель/госномер/цвет), priceBase Int?, priceTotal Int?, createdAt, confirmedAt? }`;
  enum `TaxiOrderStatus { DRAFT NEW CONFIRMED COMPLETED CANCELLED }`.
  -onDelete-политики: удаление города каскадно чистит его цены-пары и **сбрасывает DRAFT-черновики**, но сервис отклоняет удаление (`400`), если на город ссылается оформленный заказ (FK Restrict — страховка от обхода API); удаление слота оставляет заказам снимок-строку (`SetNull`); машины уходят с водителем (`Cascade`), но удаление водителя/машины с активным заказом (`NEW`/`CONFIRMED`) отклоняется (`400`), а на завершённых заказах `carId` обнуляется (`SetNull`) — отображение держится на снимке.

\_Альтернативы:\_FK без снимков — переименование/удаление справочников меняло бы прошлые заказы; Full Json-снимок всего заказа — сложнее типизировать и валидировать; отдельная таблица черновика — дублирует форму `TaxiOrder`, шаг-автомат и так нуждается в тех же полях.

### D2. Сервисы: entity-CRUD отдельно от use-case

- `TaxiCatalogService` (entity-CRUD): города, услуги, слоты, варианты пассажиров, водители и их машины; валидация уникальности и форматов; правило удаления города (черновики сбросить, оформленные заказы — `400`).
- `TaxiPriceMatrixService` (use-case): чтение матрицы, `setPairPrice` (upsert с нормализацией), `autoCalc(price)` (D5), `pairPrice(fromId, toId)` для визарда.
- `TaxiOrdersService`: список (с пассажиром через `include`, фильтр статуса: по умолчанию `NEW`+`CONFIRMED`, черновики исключены) и смена статуса.
- `TaxiCarAssignmentService` (use-case, `services/taxi-car-assignment.service.ts`): `assignFreeCar(passengerCount, requiredFeatureIds)` — подбор свободной машины по D11 (возвращает машину с водителем или `null`); проверки «занята/освобождена» и запрет удаления занятой машины/водителя в `TaxiCatalogService` опираются на тот же критерий занятости.
- `TaxiPlugin` (use-case визарда, `backend/src/plugins/taxi.plugin.ts`): машина состояний поверх черновика; реплики через `PrismaService`-независимый паттерн диспетчера — плагин возвращает `BotPluginReply`, сохранение делает `BotPluginsService`.
- Контроллеры: `TaxiCatalogController` (5 подресурсов), `TaxiPriceMatrixController`, `TaxiOrdersController` — каждый под `@UseGuards(ApiKeyGuard, AdminGuard)` с Swagger-обвязкой по образцу `AdminUsersController`.

_Альтернативы:_ один `TaxiService`-фасад — нарушает skill `service-layer-split` (микс CRUD и use-case), будет монстром при росте; контроллер на каждую сущность — 8 файлов с одинаковым guard-шаблоном.

### D3. Валидация и ошибки — в сервисах, DTO со Swagger

Каждая ошибка из спеков — `BadRequestException` (пустые поля, отрицательные значения, `HH:MM` вне `^([01]\d|2[0-3]):[0-5]\d$`, некорректный статус), `ConflictException` (дубликаты имени города/услуги/слота/`count`/госномера), `NotFoundException` (несуществующие id). DTO-классы в `src/dto/taxi-*.dto.ts` с `@ApiProperty`, ответы ошибок — существующий `ApiErrorDto`. Поля SDK наследуют обязательность из аннотаций (guard-эндпоинты держат `x-api-key` с `required: false`).

### D4. Визард — конечный автомат поверх одной строки-черновика

- **Состояние:** строка `TaxiOrder` со `status: DRAFT` и `draftStep` (1..6); `serviceIds` — массив id выбранных услуг. Не более одного DRAFT на пользователя: `/taxi` делает upsert (существующий черновик продолжается, поля перезаписываются только при рестарте — см. сценарий «Продолжение после перезапуска»).
- **Payload-формат:** `taxi:from:<cityId>`, `taxi:to:<cityId>`, `taxi:slot:<slotId>`, `taxi:pax:<optionId>`, `taxi:svc:<serviceId>:<page>` (toggle с текущей страницей), `taxi:page:<n>` (навигация порций), `taxi:done`, `taxi:confirm`, `taxi:cancel`. Длина ≤ 37 байт (префикс + cuid 25 + страница) — запас до лимита Telegram 64 байта; юнит-тест фиксирует максимум.
- **canHandle:** `kind === 'BUTTON' ? startsWith('taxi:') : trimmed.toLowerCase() === '/taxi'`; `handlesCallbacks = true`. Namespace `taxi:` не пересекается с `settings:` и пресетами оператора.
- **Реплики:** таблица `TEXTS: Record<Language, {...}>` по образцу `SettingsPlugin` (BACKLOG #5 — общий i18n отложен); каждый шаг — заголовок «Шаг N/6: …» + кнопки. Услуги помечаются `✓ ` как маркер выбора.
- **Пагинация длинных списков (лимит платформы — 12 кнопок):** шаги 1–5 рендерят активные варианты порциями по `PAGE_SIZE = 8` (хелпер `pagedReply`); худшая страница — 8 вариантов + «Назад» + «Далее» + «Готово» + «Отмена» — ровно `MAX_BUTTONS = 12`. Без этого шаг с >12 кнопками падал бы в `validateButtons`, а диспетчер молча закрыл бы задачу без ответа (пользователь видел бы тишину после нажатия). Страница живёт только в payload: навигация `taxi:page:<n>`, toggle услуги `taxi:svc:<id>:<page>` — выбор услуги остаётся на текущей странице; в БД страница не хранится (миграция ради UX-мелочи не оправдана), заголовок шага получает суффикс «страница N из M» только при M > 1, страницы вне диапазона клэмпятся к краю.
- **Правка на месте и «Назад» (D12/D13):** переходы шагов, страницы и toggle услуг возвращают реплику с `editLast` — диспетчер обновляет сообщение предыдущего шага вместо нового; «Назад» на странице 1 шагов ≥2 откатывает `draftStep` на шаг назад (черновик сохраняется), повторный выбор сбрасывает нижестоящие поля; на шаге 1 кнопки «Назад» нет.
- **Устаревшие нажатия:** payload, не соответствующий `draftStep`, или `taxi:*` без активного черновика → вежливый ответ «визард неактивен, отправьте /taxi» (возврат reply, никогда не throw — иначе диспетчер глотает и пользователь видит тишину).
- **Подтверждение:** цена из `TaxiPriceMatrixService.pairPrice`; нет цены → отказ с предложением `/taxi`, черновик сохраняется (не ломается). Есть цена → подбор свободной машины через `TaxiCarAssignmentService` (нет кандидата — отказ-реплика «нет свободной машины», черновик остаётся); при кандидате в одной транзакции статус `NEW`, `carId` + снимки (`fromCityName`, `toCityName`, `departureSlotLabel`, `serviceSnapshot` = названия+наценки, `carSnapshot` = водитель/машина, `priceBase`, `priceTotal`, `confirmedAt`), ответ с номером заказа, машиной и водителем.
- **Отмена/завершение:** черновик удаляется (`cancel`) или финализируется (`confirm`) — устаревшие кнопки старого сообщения после этого получают «визард неактивен».

_Альтернативы:_ держать шаг в памяти процесса — теряется при рестарте и не работает в cluster; передавать всё состояние в callback_data — не хватает 64 байт Telegram и данные устаревают между шагами.

### D5. Авторасчёт матрицы

`autoCalc(price)` (price — целые рубли ≥ 0): активные города сортируются по `distanceKm`; крайние — min/max; `totalKm = max − min` (при `totalKm = 0` → `400`). Для каждой неупорядоченной пары `(i, j)`: `pricePair = round(|km_i − km_j| × price / totalKm)`. Пара крайних пунктов получает `round(totalKm × price / totalKm) = price` точно. Все пары upsert'ятся (перезапись существующих цен, без суммирования). Сид не создаёт цен — матрица заполняется админом вручную или авторасчётом.

_Альтернативы:_ хранить только price-per-km и считать пары на лету — визард и админка показывали бы разные числа после правки км; хранить цены всех пар — выбранный вариант (прозрачная админ-таблица, ручная правка любой пары).

### D6. Нормализация пары цен

Пара хранится один раз: в БД `fromCityId < toCityId` лексикографически (`@@unique([fromCityId, toCityId])`). `setPairPrice` и `pairPrice` нормализуют вход (обмен местами при обратном порядке) — симметричность получается сама, второй запрос не нужен.

_Альтернативы:_ хранить обе направленности — рассинхрон при правке; искать в обоих направлениях при чтении — лишний запрос и неуникальные строки.

### D7. Сид справочников — расширение SeedService

`SeedService` при старте для каждого справочника проверяет пустоту таблицы и засеивает только пустую: 7 городов (Москва 0, Тверь 167, Вышний Волочёк 297, Бологое 377, Великий Новгород 531, Чудово 585, Санкт-Петербург 700), 9 услуг с наценками 0–500 ₽, 4 слота, варианты 1–4. Idempotent: частично изменённые справочники не трогаются (соответствует спеку «Повторный запуск»).

### D8. Фронтенд — раздел `/taxi` с сайдбаром

- Navbar: ссылка «Такси» (`session.isAdmin()`) → `/taxi`.
- `TaxiAdminLayoutComponent` (`/taxi`, `requireAdminGuard`): сайдбар слева (7 пунктов с `routerLinkActive`), справа `<router-outlet>` для дочерних маршрутов.
- Дочерние lazy-роуты: `cities`, `services`, `departure-slots`, `passenger-options`, `drivers`, `prices`, `orders` — по одному standalone-компоненту; «prices» содержит поле ввода цены крайних пунктов + кнопку «Рассчитать автоматически» и таблицу пар с правкой; «drivers» — список водителей с вложенными машинами (добавление/удаление машин из карточки водителя, у машины — вместимость и чекбоксы возможностей-услуг `isCarFeature`); «orders» — таблица с колонкой назначенной машины/водителя, фильтром статуса и select'ом смены статуса.
- `taxi.service.ts` поверх сгенерированного SDK; формы — сигналы + `[ngModel]`/`(ngModelChange)` (ловушка «computed по не-сигналам замораживает кнопку отправки»), select'ы — `[selected]` вместо `ngModel+[value]`; буквенные `@` в шаблонах — `&#64;`.

### D9. Тестирование

- **Юнит (Vitest):** `taxi-catalog.service.spec.ts` (валидация/дубликаты/правила удаления города и занятой машины), `taxi-price-matrix.service.spec.ts` (математика авторасчёта, симметрия, перезапись, <2 городов), `taxi-car-assignment.service.spec.ts` (вместимость, покрытие возможностей, занятость, best-fit, освобождение после COMPLETED/CANCELLED), `taxi-orders.service.spec.ts` (фильтр по умолчанию, смена статуса), `taxi.plugin.spec.ts` (переходы шагов, toggle услуг, «Готово» без услуг, отказ без цены, отказ без свободной машины, устаревшие кнопки, черновик-продолжение, тексты `ru`/`en`, ≤64 байта payload), обновление спека-теста сидов.
- **E2E (SDK, живой бэкенд):** `taxi-admin.e2e-spec.ts` — CRUD всех справочников + матрица (ручная пара, авторасчёт, симметрия) + заказы (смена статуса, дефолтный фильтр, назначенная машина в ответе); `taxi-wizard.e2e-spec.ts` — визард через `POST /chat/messages` + callback-нажатия (история + SSE), подтверждение → заказ в админ-списке с назначенной машиной; сценарии автоподбора (два заказа занимают две машины, COMPLETED освобождает машину, отказ при отсутствии свободной). Канон `e2e-fixture-hygiene`: все операции от test-spawned ADMIN-ключа (ActivityHelper), cleanup только собственных записей, сидовые справочники не удалять и не переименовывать (нужны другим тестам).
- **Фронт (Jest):** спеки layout'а (сайдбар/дочерний outlet), страниц городов и матрицы (авторасчёт-кнопка вызывает сервис), заказов (таблица/статус); `npm test`, не `npx jest`.
- **Порядок:** миграция → `generate:openapi-ts` → юнит → e2e → `npm test` → `ng build`.

### D10. Контракт и SDK

После бэкенд-части: `start:dev` → перегенерация `swagger.json` → `npm run generate:openapi-ts` → фронт-сервис и e2e пишутся против свежего SDK. Ломающих изменений существующих эндпоинтов нет.

### D11. Автоназначение машины при подтверждении заказа

- **Запрос пассажира → требования к машине**: `seats >= passengerCount` и оснащение машины покрывает все выбранные услуги с `isCarFeature: true` (детское кресло, курение в салоне и т.п.). Обычные услуги (вода, зарядка) подбор не ограничивают — они не требуют оснащения.
- **«Свободна»**: на машине нет активного заказа — нет `TaxiOrder` со статусом `NEW`/`CONFIRMED` и `carId = эта машина`. Время слотов не учитывается (упрощение первой версии — см. Risks).
- **Выбор (best-fit)**: среди активных (`isActive`) машин активных водителей, подходящих по вместимости и оснащению, — минимальная достаточная вместимость (большие машины остаются большим компаниям); при равной вместимости — раньше добавленная. Услуги-возможности отключённые (`isActive: false`) в требования не попадают — пассажир их выбрать не мог.
- **Фиксация**: подбор и подтверждение — в одной транзакции: `carId` + снимок `carSnapshot {driverName, model, plate, color}` — отображение заказа не зависит от последующих правок и удалений.
- **Освобождение**: перевод заказа в `COMPLETED`/`CANCELLED` снимает занятость автоматически (машина определяется по `carId` активного заказа); удаление занятой машины/водителя отклоняется `400`.
- **Отказ**: кандидатов нет → реплика «сейчас нет свободной машины под запрос — измените кол-во человек/услуги или повторите позже»; заказ не сохраняется, черновик остаётся — пользователь может снизить требования и подтвердить повторно.

_Альтернативы:_ ручное назначение админом — противоречит требованию «автоматически»; назначение при `NEW → CONFIRMED` админом — пассажир не узнаёт машину при оформлении; планирование машин по слотам с расписанием — заметно сложнее, отложено.

### D12. Правка сообщений визарда на месте (edit-in-place)

- **Контракт:** `BotPluginReply` получает опциональный флаг `editLast` (только объектная форма `{ text, buttons?, editLast? }`). Флаг означает «обнови последнее сообщение бота диалога, а не создавай новое». Строковые реплики остаются новыми сообщениями.
- **Диспетчер:** при `editLast` в той же транзакции, где закрывается задача плагина, диспетчер находит последнее BOT-сообщение диалога (ранее триггера — BUTTON-триггер сам им не является) и обновляет ему `content` + `buttons` вместо `message.create`; событие чата публикуется с признаком правки (`edited: true`). Цели нет — фолбэк на обычное новое сообщение. Повторные правки того же сообщения разрешены; правка идемпотентна при переигрывании задачи свипом восстановления (плагин перерисовывает шаг из черновика).
- **Правила не меняются:** препроцессинг реплики (trim, валидация ≤12 кнопок, payload ≤64 байт) применяется к правкам так же, как к новым сообщениям; правится только последнее BOT-сообщение самого плагина — кнопки пресетов оператора и чужих плагинов не трогаются (принцип «buttons — снапшот» касается производных от пресетов сообщений; сообщение визарда — его собственное).
- **Telegram-мост:** `Sender.sendMessage` возвращает `message_id`, мост сохраняет его в `Message.telegramMessageId` отправленной BOT-строки (best-effort: не сохранили — правка уйдёт новым сообщением). Исходящее событие с признаком правки доставляется `editMessageText(chatId, messageId, { text, reply_markup })`; без сохранённого id — fallback `sendMessage` с обратной записью нового id.
- **Клиенты:** SSE-событие несёт `edited: true`; `/chat` и `/mock-bot` заменяют содержимое пузыря по `messageId` (текст + кнопки), не добавляя новое. История `GET /chat` возвращает актуальную строку — пользователь видит только финальный экран шага; оператор по-прежнему видит все BUTTON-нажатия в консоли.
- **Границы применения в визарде:** `editLast` ставят переходы шагов 1→…→6, страницы (`taxi:page`), toggle услуг, «Готово» → экран подтверждения и «Назад» на предыдущий шаг (D13). Терминальные реплики — новыми сообщениями: чек заказа, отказы `noPrice`/`noCar` (черновик остаётся на шаге 6 — повторное «Подтвердить» работает как раньше и e2e-сценарий не ломается), «визард неактивен», ответ об отмене.

_Альтернативы:_ слать каждое состояние шага новым сообщением — лента засоряется, в Telegram inline-визарды традиционно живут правкой одного сообщения; править произвольное сообщение бота — риск испортить чужие реплики; выбрана цель «последнее BOT-сообщение диалога» с фолбэком.

### D13. Навигация «Назад» между шагами

- **Семантика кнопки:** шаг ≥ 2 рендерит «Назад» на каждой странице: страница > 1 — предыдущая порция (payload `taxi:page:<n-1>` как раньше), страница 1 — предыдущий шаг (новый payload `taxi:back`). Шаг 1 кнопки «Назад» не имеет. Бюджет кнопок не растёт: 8 вариантов + «Назад» + «Далее» + «Готово» + «Отмена» ≤ 12.
- **Состояние:** возврат ставит `draftStep = N−1`, поля черновика не трогаются; повторный выбор параметра на шаге N записывает своё поле и сбрасывает нижестоящие (`to`, slot, pax, services) — иначе после смены отправления черновик нёс бы несогласованную пару городов и цену. Сценарий «Повторный выбор после возврата» в спеке.
- **Устаревшие кнопки не реанимируются:** после возврата на шаг 1 нажатие кнопки шага 4 всё ещё «не соответствует draftStep» → реплика «визард неактивен» (спека дополнена сценарием).

### D14. Кнопки правки и удаления водителя в админке

- В задаче 7.3 методы `onDriverEdit`/`onDriverDelete` и форма в режиме «Редактировать водителя» реализованы, но кнопки в шаблоне карточки не отрисованы — в UI правки и удаления водителя не видно вовсе (обнаружено пользовательским прогоном).
- Карточка водителя получает кнопки «Изменить» (заполняет форму значениями водителя и скроллит к ней) и «Удалить» (существующий confirm; занятый активным заказом водитель вернёт `400` — текст ошибки уже выводится над списком). Правка машины не входит в объём: машину можно удалить и добавить заново.
- Jest-спек карточки: кнопки вызывают существующие `updateDriver`/`removeDriver` из `taxi.service.ts`, активируется режим правки.

## Risks / Trade-offs

- [Ошибки плагина доходят до пользователя только репликой] → все ветки отказов визарда возвращают `BotPluginReply`; юнит-тест «ошибка цены/устаревшая кнопка → reply, не throw».
- [Payload кнопок и лимит Telegram 64 байта] → префикс 10 байт + cuid 25 байт ≤ 36; тест на максимальную длину; мост и так отбрасывает превышение — визард не попадает под это.
- [Справочник длиннее лимита кнопок рендерил бы шаг молча] → при >12 кнопках шага `prepareReply` признаёт реплику невалидной: диспетчер залогирует ошибку и закроет задачу без ответа (обнаружено e2e на 12 активных услугах). Пагинация с бюджетом кнопок (8 вариантов + 4 служебные = 12) закрывает класс целиком для шагов 1–5; юнит-тесты порций/навигации/клэмпа страниц и инварианта ≤12 кнопок на каждой странице.
- [Заброшенные DRAFT-строки живут вечно (невидимы в админке)] → максимум одна на пользователя (upsert при `/taxi`); объём приемлем; чистка по расписанию — не требуется.
- [Округление авторасчёта даёт ±1 ₽ на промежуточных парах] → зафиксировано в спеке («с точностью до округления»); крайняя пара точна.
- [`AppModule`-правка легко теряется при дроблении коммитов] → в tasks.md отдельная задача регистрации всех провайдеров (3 контроллера, 3 сервиса, плагин, запись в фабрике `BOT_PLUGINS`) с проверкой `tsc` и смоук-тестом маршрутов.
- [E2E-тесты против сидовых справочников] → тесты создают собственные города/услуги (префикс `e2e-`) и удаляют их в cleanup; сидовые записи read-only в тестах.
- [Конкурирующие сессии одного пользователя (два устройства)] → одна строка-черновик, последнее нажатие выигрывает; для сценария «один пользователь — один заказ» приемлемо.
- [Матрица без цен блокирует подтверждение] → визард явно сообщает и предлагает `/taxi`; авторасчёт заполняет матрицу одной кнопкой.
- [Гонка двух одновременных подтверждений за одну машину] → подбор и назначение внутри транзакции подтверждения; при масштабе проекта (единичные заказы) коллизия маловероятна; строгая блокировка — после Redis (в BACKLOG).
- [«Свободна» не учитывает время слотов: заказы на разные слоты делят одну машину] → осознанное упрощение первой версии (D11); расписание машин по слотам — при росте нагрузки, когда появится реальная эксплуатация.
- [История показывает только финальное состояние визарда] → промежуточные экраны шагов не сохраняются (строка сообщения перезаписывается); для расследований оператор видит все BUTTON-нажатия в консоли мок-бота, снимки заказа фиксируются при подтверждении. Осознанный компромисс правки на месте (D12).
- [Правка в Telegram требует сохранённого message_id] → id пишется best-effort после отправки; потеря (ошибка записи, сообщение до внедрения механики) деградирует правку в новое сообщение — поведение остаётся корректным, возможен дубль экрана в Telegram только в legacy-случае.

## Migration Plan

1. `backend/`: миграция `add_taxi_plugin` (`npx prisma migrate dev --name add_taxi_plugin`) + `npx prisma generate` — аддитивно, до кода.
2. Код бэкенда: DTO → сервисы → контроллеры → плагин → регистрация в `AppModule` (включая `inject`-фабрику `BOT_PLUGINS`) → расширение SeedService.
3. `swagger.json` + SDK; фронт: сервис, layout, 7 страниц, роуты, navbar.
4. Тесты (юнит → e2e → Jest) и документация (`backend/README.md`, `frontend/README.md`, `docs/architecture.md`).
5. Прод: `prisma migrate deploy` перед новой версией; откат кода безопасен — таблицы самостоятельны, старый код их не читает.
