# Spec Delta

## Purpose

Вход в веб-интерфейсы (чат пользователя и консоль мок-сервера бота) по API-ключу: проверка введённого ключа на бэкенде, страница входа на фронте, хранение ключа в браузере и автоматическая передача его во всех последующих взаимодействиях с бэкендом.

## ADDED Requirements

### Requirement: Вход по API-ключу через бэкенд

Система SHALL предоставлять эндпоинт `POST /api/v1/auth/login`, который принимает введённый API-ключ, проверяет его по тем же правилам, что и `ApiKeyGuard` (ключ существует, активен, не истёк, владелец активен), и возвращает профиль в том же контракте, что и `GET /api/v1/auth/me` (пользователь + метаданные ключа; секрет ключа не раскрывается повторно).

#### Scenario: Успешный вход валидным ключом

- **WHEN** POST `/api/v1/auth/login` вызван с валидным активным ключом
- **THEN** ответ `200` содержит профиль: пользователь (id, email, role, isActive) и метаданные ключа (id, name, маскированное значение)

#### Scenario: Неверный или недействительный ключ

- **WHEN** POST `/api/v1/auth/login` вызван с несуществующим, неактивным, истёкшим ключом либо ключом неактивного пользователя
- **THEN** ответ `401` с телом ошибки, ключ не принимается

#### Scenario: Ключ не передан

- **WHEN** POST `/api/v1/auth/login` вызван без ключа (пустое тело или пустое поле apiKey)
- **THEN** ответ `400` с телом ошибки

### Requirement: Страница входа на фронтенде

Фронтенд SHALL предоставлять страницу входа (`/login`), где пользователь вводит API-ключ; введённый ключ SHALL сохраняться в браузере и восстанавливаться после перезагрузки страницы, пока пользователь не выполнит выход.

#### Scenario: Успешный вход на странице входа

- **WHEN** пользователь вводит валидный API-ключ на `/login`
- **THEN** ключ сохранён, показан профиль вошедшего пользователя, выполнен переход на целевую страницу

#### Scenario: Ввод неверного ключа

- **WHEN** пользователь вводит недействительный API-ключ на `/login`
- **THEN** показано сообщение об ошибке, ключ не сохраняется, сессия не открывается

#### Scenario: Перезагрузка страницы после входа

- **WHEN** пользователь перезагружает страницу после успешного входа
- **THEN** сессия восстанавливается из сохранённого ключа без повторного ввода

### Requirement: Передача ключа в последующих запросах

После входа фронтенд SHALL передавать сохранённый ключ во всех последующих запросах к бэкенду: в заголовке `x-api-key` для обычных HTTP-запросов и в query-параметре `apiKey` для SSE-подключений (EventSource не может задавать заголовки).

#### Scenario: Обычный HTTP-запрос после входа

- **WHEN** авторизованная страница выполняет любой API-запрос к бэкенду
- **THEN** запрос содержит заголовок `x-api-key` со сохранённым ключом

#### Scenario: SSE-подключение после входа

- **WHEN** авторизованная страница открывает SSE-подключение к потоку бэкенда
- **THEN** URL подключения содержит query-параметр `apiKey` со сохранённым ключом

### Requirement: Защита страниц и завершение сессии

Страницы чата и консоли мок-сервера SHALL требовать открытую сессию: без сохранённого ключа пользователь перенаправляется на `/login`. Выход SHALL удалять сохранённый ключ. Получение от бэкенда ответа `401` SHALL завершать сессию с перенаправлением на `/login`.

#### Scenario: Переход на защищённую страницу без входа

- **WHEN** пользователь открывает `/chat` или `/mock-bot` без сохранённого ключа
- **THEN** выполняется перенаправление на `/login`

#### Scenario: Потеря валидности ключа во время работы

- **WHEN** бэкенд возвращает `401` на запрос авторизованной страницы
- **THEN** сохранённый ключ удаляется и пользователь перенаправляется на `/login`

#### Scenario: Выход из системы

- **WHEN** пользователь выполняет выход
- **THEN** сохранённый ключ удаляется и выполняется перенаправление на `/login`
