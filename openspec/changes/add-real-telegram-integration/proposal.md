# Proposal

## Why

Сегодня бот живёт только внутри веб-интерфейсов: пользователь пишет в `/chat`, ответ формирует движок разговора (плагины + консоль оператора-«мока»). Реального Telegram нет ни в одном из изменений (`add-web-chat-with-mock-bot`, `add-bot-plugin-system`, `add-user-settings-language-plugin` прямо откладывали интеграцию). Продукту нужен вывод той же диалоговой логики на настоящий канал Telegram: админ заводит несколько боевых ботов, привязывает к ним пользователей, и переписка идёт через Telegram так, будто пользователь пишет в мок-сервер, — без переписывания плагинов и консоли.

## What Changes

- Админ заводит **несколько Telegram-ботов** (каждый со своим токеном, именем и набором настроек) и может создавать/изменять/удалять их, а также **включать и выключать** каждый. Боты принадлежат создавшему их админу (owner-scope, как `ButtonPreset`).
- Каждый бот имеет **собственный адрес вебхука** и при старте приложения **самостоятельно регистрирует** его в Telegram (setWebhook) — best-effort: ошибка сети/Telegram не роняет старт, а логируется.
- **BREAKING** (поведенческое, только для новых состояний): у пользователя появляется **активная цель** — конкретный Telegram-бот либо **мок-сервер** (значение по умолчанию, прежнее поведение). Админ переключает её у любого пользователя в любой момент.
- Когда активная цель — Telegram-бот (а не мок), в навигации пользователя появляется кнопка **«Запустить телеграм бота»**. По нажатию выдаётся deep-link `t.me/<bot>?start=<токен>`; когда пользователь открывает Telegram, бот через вебхук получает `/start <токен>` и **привязывает** Telegram `chat id` к этому аккаунту.
- **Двусторонний мост**: входящее сообщение/нажатие inline-кнопки из Telegram попадает в диалог пользователя тем же путём, что набор текста в веб-чате (тот же outbox + диспатч плагинов); любой ответ бота в этом диалоге пересылается пользователю в Telegram тем же ботом (текст + inline-клавиатура). Кнопочная логика проксируется в обе стороны.
- Переключение пользователя обратно на мок-сервер **немедленно останавливает** проксирование сообщений и кнопок.
- Веб-чат при включённом привязанном боте продолжает работать (сообщение уходит в диалог, ответ дублируется в Telegram). Если привязанный бот **выключен**, отправка сообщения/нажатие кнопки в веб-чате возвращает **понятную ошибку**, а не молча проходит.

## Capabilities

### New Capabilities

- `telegram-bots`: owner-scope CRUD Telegram-ботов админом, включение/выключение, хранение токена и настроек, собственный секрет вебхука и самостоятельная регистрация/снятие вебхука при старте и при изменениях (best-effort).
- `telegram-user-binding`: назначение пользователю активной цели (бот или мок-сервер) админом; кнопка «Запустить телеграм бота» и deep-link-привязка Telegram `chat id` к аккаунту; идемпотентность и сброс привязки при смене цели.
- `telegram-message-bridge`: сквозной прокси текста и inline-кнопок между Telegram и движком разговора; входящие обновления вебхука → в диалог как сообщение пользователя; исходящие `BOT`-ответы → наружу через привязанный включённый бот; остановка моста при возврате на мок и понятная ошибка при выключенном привязанном боте.

### Modified Capabilities

- `user-chat` (`openspec/specs/user-chat/spec.md`): отправка сообщения и нажатие кнопки остаются успешными, когда активная цель — мок или **включённый** бот (ответ дополнительно уходит в Telegram), но возвращают понятную ошибку, когда активная цель — **выключенный** бот.

## Impact

- Новая runtime-зависимость `backend`: **grammy** (`npm i grammy`) для Telegram Bot API (вебхуки, setWebhook, sendMessage с inline-клавиатурой, answerCallbackQuery).
- `backend/prisma/schema.prisma` + миграция: модель `TelegramBot` (`ownerId`, `name`, `botToken`, `isActive`, секрет/URL вебхука, необязательные настройки) и поля у `User` — активный бот + привязанный Telegram `chat id`.
- `backend/src/`: новый entity-CRUD `TelegramBotsService`, use-case `TelegramBindingService`, инфраструктурный `TelegramBridgeService` (подписка на `ChatEventsService` + вебхук-диспатчер), `TelegramWebhookController` (публичные маршруты вебхуков с проверкой секрета), DTO-классы со Swagger, админ-эндпоинты CRUD/назначения. Регистрация — только в `backend/src/app.module.ts` (один модуль).
- `main.ts`/bootstrap: регистрация вебхуков включённых ботов при старте (через `OnApplicationBootstrap`, как `BotPluginsService`/`SeedService`).
- `backend/src/services/chat.service.ts`: проверка активной цели и статуса бота на путях `sendMessage`/`submitButtonCallback` (ошибка при выключенном боте).
- Фронтенд: `navbar.component.ts` — условная кнопка «Запустить телеграм бота»; сервис запуска/привязки; экран/админ-консоль управления ботами и назначения цели.
- Тесты: юнит-плейсы новых сервисов + `*.spec.ts`; e2e через SDK на живом бэкенде (CRUD ботов, назначение, состояние ошибки) с external-границей Telegram, замоканной; обновление спецификаций `frontend` для кнопки навигации.
- Документация: `README.md`, `docs/architecture.md`, `docs/environment.md` (env публичного базового URL вебхуков), `BACKLOG.md` (polling-фолбэк, media/кэпшены, rate-limit).
- Вне рамок: медиа/фото и лимиты кэпшенов, исходящие инициативные рассылки, обработка `my_chat_member`/`edited_message`, polling-режим как основная доставка, i18n текстов моста, распределённая блокировка в cluster (остаётся долг из BACKLOG #1/#2).
