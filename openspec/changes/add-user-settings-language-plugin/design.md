# Design

## Context

См. proposal.md (Why) и `specs/*` (что именно гарантируется). Подход определяют эти факты текущего состояния:

- Контракт плагина — `backend/src/plugins/bot-plugin.interface.ts`: `canHandle(content)` + `handle(ctx) → string`; ответ всегда текст (`BotPluginContext` = `{ user, content }`).
- `BotPluginsService.dispatchAndReply` атомарно закрепляет outbox-задачу (`PENDING → PROCESSING`), сохраняет `BOT`-сообщение и закрывает задачу в одной транзакции, публикует событие в `ChatEventsService`; ошибка плагина логируется и не влияет на отправку. Recovery-sweep догоняет `PENDING` и перезревшие `PROCESSING`.
- `ChatService.submitButtonCallback` сейчас **намеренно** не создаёт `BotPluginTask` и не зовёт диспетчер; `kind=BUTTON` фильтруется из истории (`getHistory`) и из SSE пользователя (`streamEvents`), но остаётся виден оператору (`MockBotController.streamAll`). Фронтенд (`chat.component.ts`) рендерит кнопки у `BOT`-сообщений и шлёт payload на `POST /chat/button-callbacks`, ответ которого игнорирует.
- `Message.buttons` — неизменяемый снимок `Json`-кнопок; их валидация/нормализация уже есть в `backend/src/utils/keyboard-buttons.ts` (`validateButtons`, `normalizeButtons`, `toButtons`; лимиты 12 / 64 / 256).
- Профиль собирает `AuthService.profile`/`toProfile`; самообновление — `PATCH /auth/me` с одним необязательным `timezone`, валидация в сервисе (глобального `ValidationPipe` в `main.ts` нет).
- Схема меняется только миграциями Prisma; enum/типы импортируются из `src/generated/prisma/enums.js`, модели — из `.../client.js`. Плагины регистрируются фабрикой `BOT_PLUGINS` в `backend/src/app.module.ts`; порядок инъекции = приоритет.
- E2E идут через сгенерированный SDK на живом бэкенде; после изменения контракта — `start:dev` → `npm run generate:openapi-ts` → `test:e2e`.

## Goals / Non-Goals

**Goals:**

- Один источник правды для активного языка: колонка `User.language`, значения `ru`/`en`, дефолт `en`.
- Плагин `settings` как единственный пользовательский экран настроек: просмотр по `/settings` и смена языка нажатием кнопки, всё внутри существующего чата.
- Обратимо расширяемый контракт плагинов: «принимать нажатия кнопок» и «отвечать кнопками» — необязательные способности, по умолчанию поведение прежнее.
- Те же гарантии надёжности для нажатия, что и для текста: outbox-задача, ровно одна обработка, доведение после рестарта, изоляция ошибок плагина.
- Отсутствие правок фронтенда: ответ с кнопками и подтверждение используют уже существующие каналы (история, SSE, рендер кнопок).

**Non-Goals:**

- Перевод остальных текстов бота (`pong`, `time`, ответы оператора, сообщения консоли) и любой фреймворк i18n — только поле настройки и тексты плагина `settings`.
- Язык интерфейса Angular-приложения, автоопределение языка браузера (в отличие от таймзоны — синхронизации `navigator.language` не делаем).
- Другие пункты настроек (тема, уведомления), админский CRUD настроек, отдельный REST-эндпоинт смены языка.
- Авто-registration плагинов (убрать правку `AppModule`) — остаётся долгом в BACKLOG.md.

## Decisions

### D1. Язык — Prisma-enum с нижнерегистровыми участниками (первоначальный `@map` не сработал)

`backend/prisma/schema.prisma`:

```prisma
enum Language {
  en
  ru
}

model User {
  ...
  language Language @default(en)
}
```

План был `EN @map("en")` / `RU @map("ru")`, чтобы сохранить UPPER-конвенцию enum-значений схемы. При реализации (Prisma 7.10, генератор `prisma-client`) проверено: `@map` значений enum применяется к SQL (миграция создаёт `CREATE TYPE "Language" AS ENUM ('en','ru')`), но в сгенерированный клиент не переносится — `Language.EN` выводился как `'EN'`, то есть клиент писал бы `'EN'` в домен `('en','ru')`. Поэтому выбран задокументированный в Risks fallback: участники `en`/`ru` без `@map`. Побочных правок нет: домен БД, тип поля (`"en" | "ru"`) и wire-формат API совпадают с первоначальным замыслом, применённая миграция остаётся корректной, новая не требовалась.

Миграция — `npx prisma migrate dev --name add_user_language` (ALTER TABLE с `DEFAULT 'en'`, backfill существующих строк делает дефолт; отдельного data-migration нет).

Альтернативы: `String @default("en")` + валидация в сервисе — отклонено, нет ограничения на уровне БД и значение может «съехать» при ручном сиде; `@map` на значениях enum — отклонено по факту наблюдения выше.

### D2. Коллбэки — необязательная способность плагина, а не новый метод

`bot-plugin.interface.ts` расширяется минимально:

```ts
/** Source of the message handed to a plugin. */
export type BotPluginSourceKind = 'TEXT' | 'BUTTON';

export interface BotPluginContext {
  user: User;
  content: string; // текст сообщения или payload нажатой кнопки
  kind: BotPluginSourceKind;
}

/** Reply payload: plain text, or text with an inline keyboard. */
export type BotPluginReply = string | { text: string; buttons?: KeyboardButtonDto[] };

export interface BotPlugin {
  readonly name: string;
  /** Opt-in: the plugin also receives inline-button callbacks. Default false. */
  readonly handlesCallbacks?: boolean;
  canHandle(content: string, kind: BotPluginSourceKind): boolean;
  handle(context: BotPluginContext): Promise<BotPluginReply> | BotPluginReply;
}
```

Диспетчер для `kind === 'BUTTON'` рассматривает только плагины с `handlesCallbacks === true`, для `TEXT` — все, как сейчас. Оба шага `canHandle` вызываются по тому же принципу «первый совпавший в порядке регистрации».

Существующие `PingPongPlugin`/`TimePlugin` не меняются: `canHandle(content: string)` структурно удовлетворяет новому контракту (лишний параметр TS не ломает), `handlesCallbacks` не объявлен → их поведение и их спеки (`ping`, `time`) остаются истинными.

Альтернативы: отдельный метод `handleCallback()` — удваивает API и ветвит логику одного экрана настроек в двух местах; диспатчить коллбэки всем плагинам — нарушило бы закрепённый сценарий «payload `ping` по кнопке не даёт ответа» и требовал бы правки обеих существующих спецификаций.

### D3. Ответ с кнопками нормализует диспетчер, а не плагин

`BotPluginsService` приводит `BotPluginReply` к `{ text, buttons }`, прогоняет кнопки через существующие `validateButtons` + `normalizeButtons` и пишет снимок в `Message.buttons`, а затем в `ChatEvent.buttons`. Некорректный набор = ошибка пути ответа: логируем, задачу закрываем, сообщения бота нет (тот же контракт изоляции, что и для исключения плагина). `string`-ответ трактуется как `{ text }` — обратная совместимость без правок существующих плагинов и их юнит-тестов.

Альтернатива: плагин сам пишет `Message` — отказ, дублирование outbox/транзакционной логики и потеря exactly-once.

### D4. Путь нажатия: тот же outbox + диспатч после публикации

`ChatService.submitButtonCallback` меняется так же, как когда-то `sendMessage`:

1. `conversation.upsert` (как сейчас);
2. транзакция: `message.create({ kind: BUTTON })` + `botPluginTask.create({ messageId })` — приёмка атомарна, нажатие не может остаться без задачи;
3. публикация события `kind: 'BUTTON'` (без изменений — пользовательский поток его по-прежнему фильтрует, оператор видит);
4. `dispatchToPlugins(conversationId, user, callbackData, messageId, 'BUTTON')` в `try/catch` (ошибка диспетчера не ломает ответ запроса).

Отклик на `POST /chat/button-callbacks` остаётся DTO тихого сообщения-коллбэка: подтверждение приходит отдельным `BOT`-событием по SSE, поэтому фронтенд правок не требует. `processPendingTask` восстанавливает `kind` из `message.kind` и передаёт его в диспетчер, поэтому sweep догоняет и нажатия.

Идемпотентность побочного эффекта: повторная обработка payload `settings:language:<x>` просто ставит тот же `<x>` и шлёт то же подтверждение — ровно-одна-обработка гарантируется закрепом задачи, так что дубль сообщения невозможен, а дубль записи профиля безвреден.

### D5. Тексты — константа внутри плагина, язык ответа = целевой язык

В `settings.plugin.ts`: таблица `{ en: {...}, ru: {...} }` (заголовок настроек, подпись активного языка, подтверждение смены) + `SUPPORTED_LANGUAGES = ['en', 'ru']`. Никакого i18n-слоя: переводы нужны ровно одному плагину (см. Non-Goals), вынесение в общий модуль — за BACKLOG.md, когда появится второй потребитель.

Подтверждение смены формируется на **новом** языке (после записи профиля), экран `/settings` — на текущем. Это осознанный ответ на «после смены языка прислать сообщение, что язык успешно сменился»: пользователь должен прочитать результат на том языке, который выбрал.

### D6. Формат кнопки и пространство имён payload

`callbackData` — `settings:language:en` / `settings:language:ru`; префикс `settings:` резервирует пространство имён настроек для будущих пунктов (D2 делает его безопасным: чужой payload ни на что не наткнётся). `title` — самоназвания языков (`English`, `Русский`), они не переводятся; текущий язык помечается префиксом `✓ ` (`✓ English`), у неактивных пометки нет. Лимиты (12/64/256) соблюдены с запасом.

Триггер просмотра — строго `/settings` (trim + lower), без варианта `settings` и `/настройки`: требование сформулировано как «пользователь шлёт /settings», а мягкие совпадения конкурировали бы с будущими командами.

### D7. Язык в контракте профиля и регистрация плагина

`AuthProfileUserDto` получает `language` (enum `['en','ru']`), `UpdateProfileRequestDto` — необязательный `language`, который `AuthService.updateProfile` валидирует (`normalizeLanguage` → `BadRequestException` при значении вне набора) и пишет вместе с `timezone` в одном `user.update`. Swagger-контракт перегенерируется (`generate:openapi-ts`), что и позволит слать `language` из e2e.

`AppModule.providers`: `SettingsPlugin` + добавление его в `useFactory`/`inject` фабрики `BOT_PLUGINS` последним (пересечений с `ping`/`time` нет, но порядок фиксируем явно). Отдельного контроллера/модуля не появляется — вся пользовательская поверхность живёт в чате.

### D8. Неподдерживаемый код языка — ответ ошибкой, а не молчание

Изначально плагин на payload вне поддерживаемых кодов (`settings:language:de`, `settings:language:`, `settings:language:ru,en`) молчал: `canHandle` пропускал только валидные коды, `handle` не вызывался, и отказ нельзя было наблюдать ни в диалоге, ни в логах. Целевое поведение: плагин владеет всей областью `settings:language:` (проверка по префиксу), а неподдерживаемый код обслуживает **сообщением об ошибке**:

```ts
canHandle(content, kind) => kind === 'BUTTON'
  ? content.trim().toLowerCase().startsWith('settings:language:')
  : content.trim().toLowerCase() === '/settings';

// selectLanguage: код распознан → запись + подтверждение на новом языке;
// код не распознан → profile не трогается, ответ TEXTS[user.language].unsupported
// с подстановками {code} и {supported} + кнопки, размеченные под оставшимся активным языком.
```

Доставка — тот же путь, что у любого reply: `Message(BOT)` в транзакции с закрытием задачи + `ChatEvent`. Отклик `POST /chat/button-callbacks` при этом остаётся `201` с DTO нажатия: результат плагина (успех или ошибка) клиент всегда получает отдельным сообщением по SSE, а после падения процесса его догоняет recovery-sweep — то есть ошибка доходит асинхронно тем же каналом, что и ответ.

Исключение из плагина (`throw`) для этого случая убирается: оно было недостижимо через `canHandle` и по контракту изоляции (`bot-plugin-callbacks`, «Сбой плагина на нажатии не влияет на пользователя») превратилось бы только в запись в лог без видимого результата для пользователя.

Альтернативы: оставить тихий отказ — отказ, пользователю нечем исправить нажатую кнопку; HTTP `400` на коллбэке — отклик нажатия не знает о плагинах и не должен парсить их пространство имён, плюс сломал бы фронтенд-контракт «ответ игнорируется»; warn-лог в диспетчере для «никто не взял нажатие» — дополняет наблюдаемость для чужих payload, но не решает задачу пользователя.

### D9. Тестовая стратегия

- Юнит (`backend/src/plugins/settings.plugin.spec.ts`): форматирование экрана по `en`/`ru`, метка текущего языка, смена через `handle({kind:'BUTTON'})` (мок Prisma), идемпотентное повторное нажатие, **сообщение об ошибке на неподдерживаемом коде (оба языка, без записи в профиль)**, `canHandle` принимает всю область `settings:language:` и не срабатывает на `settings`/`/settings?`/чужие префиксы.
- Юнит `bot-plugins.service.spec.ts`: `handlesCallbacks`-фильтрация (коллбэк `ping` не уходит PingPongPlugin), persist кнопок ответа, невалидные кнопки → нет сообщения, recovery-sweep догоняет `BUTTON`-задачу.
- E2E (`backend/test/settings-plugin.e2e-spec.ts`, по канону e2e-fixture-hygiene — test-spawned ключ, не сид-админ): `POST /chat/messages` `/settings` → в истории `BOT`-сообщение с двумя кнопками; `POST /chat/button-callbacks` `settings:language:ru` → подтверждение на русском в истории, `GET /auth/me` отдаёт `language: "ru"`; `settings:language:de` → `201` на нажатие + `BOT`-сообщение об ошибке и прежний язык; `PATCH /auth/me { language: "de" }` → `400`; регрессия: payload `ping` по-прежнему не даёт ответа.

## Risks / Trade-offs

- [Нажатие кнопки больше не гарантированно «тихое»] → способность узкая: только плагины с `handlesCallbacks`, а их payload-пространство (`settings:language:`) не пересекается с пресетами оператора; сценарии «пресет-кнопка молчит» и «`ping`-кнопка молчит» зафиксированы в спеках и в e2e.
- [Область `settings:language:` целиком принадлежит плагину → битый код теперь всегда порождает сообщение бота] → осознанный размен молчания на объяснение отказа: запись профиля при этом не делается, идемпотентность сохраняется (ровно одна обработка на нажатие благодаря закрепу задачи), а повторный клик по той же битой кнопке даёт то же сообщение; чужие payload (`ping`, `presets:*`, `settings:lang:*`) по-прежнему тихие.
- [Пользователь жал кнопку из старого сообщения настроек — язык меняется «внезапно»] → принято как Telegram-семантика снимка кнопок; поведение идемпотентно и подтверждается сообщением, отдельного сценария в спеке не требует.
- [`@map` на значениях enum не устроит генератор Prisma 7] → fallback без смены контракта: участники `en`/`ru` без `@map` (wire-формат тот же, страдает только UPPER-конвенция имён); проверить сразу после `npx prisma generate` по типу `user.language`.
- [Диспатч коллбэка удваивает write-нагрузку на `POST /chat/button-callbacks`] → один дополнительный транзакционный `updateMany` + одно `message.create` на нажатие, как у текста; синхронный путь тот же, что уже проверен на `sendMessage`.
- [Лишние ответы бота в диалоге при «защитном» переиспользовании payload] → диспетчер выбирает первого совпавшего; префикс пространства имён и порядок регистрации фиксируют это, расширение настроек обязано сохранять уникальность payload'ов.
- [Подтверждение приходит по SSE, и клиент без открытого SSE увидит его только при следующей загрузке истории] → то же ограничение, что у всех ответов плагинов сейчас (шина в памяти); компенсация — перезагрузка истории при переподключении, уже реализованная на фронте.

## Migration Plan

1. `backend/prisma/schema.prisma` → `npx prisma migrate dev --name add_user_language` → `npx prisma generate` (из `backend/`).
2. Бэкенд: интерфейс → диспетчер → `ChatService` → `SettingsPlugin` → регистрация в `BOT_PLUGINS` → `AuthProfileUserDto`/`UpdateProfileRequestDto`/`AuthService`.
3. `npm run start:dev` → `npm run generate:openapi-ts` → `npm run test:e2e` (поверх существующих `chat.e2e-spec.ts`, `keyboard-buttons.e2e-spec.ts` — они не должны деградировать).
4. Документация: `README.md` (плагин `/settings`, поле `language`), `docs/architecture.md` (топология плагинов), `BACKLOG.md` (i18n остальных текстов, авто-registration плагинов).
5. Деплой: `prisma migrate deploy` перед перезапуском приложения (колонка с дефолтом — добавляется без блокирующего backfill).
6. Откат: реверт кода + `prisma migrate`-откат миграции (drop column `language`). Других потребителей у поля нет, данные не теряются критично — единственная потерянная информация ранее сделанный выбор языка.

## Open Questions

- Стоит ли помечать текущий язык галочкой `✓` или иначе (например, «текущий» в подписи) — косметика, решается на этапе вёрстки текста плагина и не влияет на спеки.
- Состав следующих настроек в этом же экране (тема, уведомления, часовой пояс) — определяется отдельным изменением.
